# CCTP strategy review — PR #10 head `b2b9c9e`

## [Medium] In-flight CCTP transfers can distort assets and share prices

### Details

Remote [`processWithdrawal()`](https://github.com/Schlagonia/tokenized-cctp/blob/b2b9c9ec509f1bf697b60a628a6ac3c5bfa2e5a1/src/bases/BaseRemoteStrategy.sol#L139) burns USDC and sends a reduced-balance report as separate CCTP V2 messages. The prepared [Circle receiver](https://github.com/circlefin/evm-cctp-contracts/blob/a92a2b4e7e6ef99bf0b05dca71780f5ec190e729/src/v2/MessageTransmitterV2.sol#L206) can deliver the mint first. The origin then [adds local USDC to its old remote balance](https://github.com/Schlagonia/tokenized-cctp/blob/b2b9c9ec509f1bf697b60a628a6ac3c5bfa2e5a1/src/bases/BaseCrossChain.sol#L51): returning 50 of 1,000 units exposes 1,050 as assets, a false 5% gain within its 10% health limit. The factory sets zero profit unlock time, while the correction meets a default zero loss limit. A later keeper tend can discard the authentic report by advancing the timestamp watermark. This is a verified source accounting path; deployed payout was not demonstrated.

### Recommendation

Reconcile burns and snapshots with transfer identifiers before reporting or settling shares against returned liquidity. Test both delivery orders, failed delivery, intervening tends, and withdrawals through the intended parent vault.

## [Medium] A positive Circle minimum fee would halt zero-fee burns

### Details

The CCTP [origin](https://github.com/Schlagonia/tokenized-cctp/blob/b2b9c9ec509f1bf697b60a628a6ac3c5bfa2e5a1/src/CCTPStrategy.sol#L42) and [remote](https://github.com/Schlagonia/tokenized-cctp/blob/b2b9c9ec509f1bf697b60a628a6ac3c5bfa2e5a1/src/CCTPRemoteStrategy.sol#L41) both pass `maxFee = 0` to V2 `depositForBurn`. The prepared [Circle implementation](https://github.com/circlefin/evm-cctp-contracts/blob/a92a2b4e7e6ef99bf0b05dca71780f5ec190e729/src/v2/TokenMessengerV2.sol#L332) rejects positive burns when its controller sets `minFee > 0`, blocking deployment or return of remote capital. The used proxies and fee settings were not established, so current deployment impact remains unresolved.

### Recommendation

Read both intended messengers’ implementations and `minFee` values, test burns under those settings, and provide a bounded fee policy or tested return path if a positive minimum is possible.

## [Low] Keeper tend can rebridge returned USDC after shutdown

### Details

The pinned [Yearn framework](https://github.com/yearn/tokenized-strategy/blob/82806289f967590c4efbf6bc3d237e4e7f0a0966/src/TokenizedStrategy.sol#L1314) keeps `tend()` callable after shutdown. The [origin tend hook](https://github.com/Schlagonia/tokenized-cctp/blob/b2b9c9ec509f1bf697b60a628a6ac3c5bfa2e5a1/src/bases/BaseCrossChain.sol#L107) burns all idle USDC without a shutdown check. An authorized keeper tending returned funds during wind-down removes immediate withdrawal liquidity and requires another remote withdrawal and relay cycle.

### Recommendation

Block outbound burns after shutdown. Test shutdown, return mint, keeper tend, and vault withdrawal in sequence.

## [Low] New origin deployment has no positive tend trigger

### Details

After commit `6263348`, deposits remain idle because [`_deployFunds()`](https://github.com/Schlagonia/tokenized-cctp/blob/b2b9c9ec509f1bf697b60a628a6ac3c5bfa2e5a1/src/bases/BaseCrossChain.sol#L103) does nothing; only keeper `tend()` bridges them. The origin inherits a pinned [`_tendTrigger()`](https://github.com/yearn/tokenized-strategy/blob/82806289f967590c4efbf6bc3d237e4e7f0a0966/src/BaseStrategy.sol#L264) that always returns false. Trigger-based keepers can leave allocated USDC idle indefinitely, although a separately scheduled tend works.

### Recommendation

Add a bounded, shutdown-aware trigger or establish and test an explicit keeper schedule from allocation to bridge.

## [Low] Zero child redeemability may block partial returns

### Details

For a request above loose remote USDC, [`_pullFunds()`](https://github.com/Schlagonia/tokenized-cctp/blob/b2b9c9ec509f1bf697b60a628a6ac3c5bfa2e5a1/src/bases/BaseRemote4626.sol#L39) calls the child vault’s `redeem(0)` when `maxRedeem` is zero. A child with the prepared [Yearn Vault V3 zero-share rule](https://github.com/yearn/yearn-vaults-v3/blob/f449264ff4f8bebe9a6bf72e43095304fdf101b8/contracts/VaultV3.vy#L776) reverts the whole withdrawal, including otherwise returnable loose USDC. The intended Base vault’s implementation was not verified; a keeper can request only the loose amount.

### Recommendation

Skip zero-share redemption and bridge available loose funds. Test an oversized request with positive loose USDC and zero `maxRedeem` against the exact child vault.

## [Informational] HyperCore settlement timing remains unverified

### Details

The Hyper remote [pushes USDC asynchronously](https://github.com/Schlagonia/tokenized-cctp/blob/b2b9c9ec509f1bf697b60a628a6ac3c5bfa2e5a1/src/HyperRemoteStrategy.sol#L176), while its [report](https://github.com/Schlagonia/tokenized-cctp/blob/b2b9c9ec509f1bf697b60a628a6ac3c5bfa2e5a1/src/HyperRemoteStrategy.sol#L82) values EVM and credited Core balances without pending deposits. If Core credit lags a later report, the origin receives a low snapshot and its zero loss limit may stall accounting. The prepared evidence does not establish that timing or the intended HLP liquidity and exit behavior.

### Recommendation

On the intended HyperEVM/Core deployment, report during a delayed credit and after settlement. Verify the origin cache, loss check, HLP lockup, liquidity, staged withdrawal, and recovery.

## [Informational] Deployed pairing and CCTP operations are unverified

### Details

The [factories](https://github.com/Schlagonia/tokenized-cctp/blob/b2b9c9ec509f1bf697b60a628a6ac3c5bfa2e5a1/src/StrategyFactory.sol#L62) define counterpart pairing, but the prepared evidence does not match PR #10 bytecode and constructor values to the issue’s addresses or identify the actual parent vault, child vault, roles, Circle proxies, relayers, and attestation service. Source inspection identifies CCTP **V2** and verifies signature, domain, nonce, sender, and finality checks in the prepared implementation; it does not prove those contracts or delivery duties are live. Current Circle technical documentation was absent from the offline snapshot.

### Recommendation

Compare deployed bytecode and fixed-block configuration with the pinned build; verify counterparts, domains, fees, pauses, vault liquidity, and parent accounting. Test attested burns, reports, failed-claim retries, and shutdown through the deployed composition, and provide a current Circle documentation snapshot.
