# Katana Cross-Chain Strategy Review — PR #10 `b2b9c9e`

## [Medium] In-flight returns can create false profit and discard corrective reports

### Details

The remote [withdrawal path](https://github.com/Schlagonia/tokenized-cctp/blob/b2b9c9ec509f1bf697b60a628a6ac3c5bfa2e5a1/src/bases/BaseRemoteStrategy.sol#L139-L174) sends the asset and its reduced-balance report separately; the prepared Agglayer bridge permits [independent claims](https://github.com/agglayer/agglayer-contracts/blob/110bda5a03e70ee7331bc06407a8e79226d3e520/contracts/AgglayerBridge.sol#L537-L564). If 50 of 1,000 remote units is claimed first, the origin [counts 1,050](https://github.com/Schlagonia/tokenized-cctp/blob/b2b9c9ec509f1bf697b60a628a6ac3c5bfa2e5a1/src/KatanaStrategy.sol#L49-L55) until the 950-unit report arrives. A keeper report can pass the 10% health limit and mint fee shares on returned principal; the correction can then hit the default zero loss limit. A keeper [tend before message claim](https://github.com/Schlagonia/tokenized-cctp/blob/b2b9c9ec509f1bf697b60a628a6ac3c5bfa2e5a1/src/bases/BaseCrossChain.sol#L75-L115) can advance the timestamp watermark and discard that valid report altogether. These are source-level paths; deployed timing and fees were not verified.

### Recommendation

Track transfers and report snapshots by explicit identifiers, and prevent reporting against unreconciled returns. Test both claim orders, delayed or failed messages, tend between send and claim, fee minting, and parent-vault accounting with the intended deployment.

## [Medium] Keeper tend can rebridge recovered funds after shutdown

### Details

The pinned Yearn framework [allows `tend()` after shutdown](https://github.com/yearn/tokenized-strategy/blob/82806289f967590c4efbf6bc3d237e4e7f0a0966/src/TokenizedStrategy.sol#L1314-L1339). The origin [tend hook](https://github.com/Schlagonia/tokenized-cctp/blob/b2b9c9ec509f1bf697b60a628a6ac3c5bfa2e5a1/src/bases/BaseCrossChain.sol#L103-L118) bridges all idle USDC without checking shutdown. If a keeper tends after a return has been redeemed during wind-down, locally withdrawable liquidity moves back to Katana and must complete another asynchronous return before withdrawal. This requires keeper authority; deployed keeper behavior is unknown.

### Recommendation

Block bridge-producing tends after shutdown. Test shutdown, return claim and redemption, keeper tend, and vault withdrawal in sequence.

## [Low] New bridge deployment path has no tend trigger

### Details

The November change leaves deposits idle in [`_deployFunds()`](https://github.com/Schlagonia/tokenized-cctp/blob/b2b9c9ec509f1bf697b60a628a6ac3c5bfa2e5a1/src/bases/BaseCrossChain.sol#L103-L115) and bridges only through keeper `tend()`. The origin does not override the pinned framework's [`_tendTrigger()`](https://github.com/yearn/tokenized-strategy/blob/82806289f967590c4efbf6bc3d237e4e7f0a0966/src/BaseStrategy.sol#L264-L279), which always returns false. Automation that relies on this trigger leaves allocated USDC idle indefinitely; a separately scheduled keeper call can bridge it.

### Recommendation

Add a positive, shutdown-aware trigger or confirm an explicit keeper schedule. Test deposit-to-bridge timing in the actual keeper workflow.

## [Low] Zero remote redeemability can block an oversized partial return

### Details

When a withdrawal request exceeds loose remote vbToken, [`_pullFunds()`](https://github.com/Schlagonia/tokenized-cctp/blob/b2b9c9ec509f1bf697b60a628a6ac3c5bfa2e5a1/src/bases/BaseRemote4626.sol#L39-L51) calls the child vault's `redeem(0)` if `maxRedeem` is zero. A vault with the prepared [Vault V3 zero-share rule](https://github.com/yearn/yearn-vaults-v3/blob/f449264ff4f8bebe9a6bf72e43095304fdf101b8/contracts/VaultV3.vy#L776-L779) reverts before the loose portion can return. A keeper can avoid this by requesting no more than the loose balance. The selected Katana vault implementation was not prepared, so applicability remains conditional.

### Recommendation

Skip zero-share redemption and bridge available loose assets. Test positive loose balance, zero `maxRedeem`, and an oversized request against the exact Katana vault.

## [Informational] Deployment and cross-chain liveness remain unverified

### Details

The [deployment script](https://github.com/Schlagonia/tokenized-cctp/blob/b2b9c9ec509f1bf697b60a628a6ac3c5bfa2e5a1/script/DeployKatanaStrategy.s.sol#L45-L104) checks predicted counterpart and vault-asset compatibility, but the prepared evidence does not match PR #10 runtime bytecode or configuration to the issue's March addresses. The Katana vault, allocating parent, keeper and claim-bot settings, vbUSDC proxy and yield-vault state, bridge finality, pauses, proof availability, and retry behavior were not verified. The supplied Polygon and Katana documentation pages were unavailable in the prepared offline evidence.

### Recommendation

Compare deployed implementations and constructor inputs with a reproducible build, identify the exact parent and Katana vault, and run two-chain claim, liquidity, pause, finality, retry, report, and shutdown tests against that composition before relying on deployed behavior.
