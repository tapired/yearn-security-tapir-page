# Flex Allocator post-cutover security review

## [Medium] Settlement-token donations can repeatedly block reports

### Details

`FxSaveStrategy.pendingRedemptions()` counts the strategy’s raw FXUSD balance, while `AvantStrategy.pendingRedemptions()` counts raw AVETH. Any account able to transfer these tokens can donate just over the pending threshold—approximately `0.001` FXUSD or `1e9` AVETH wei—and make `_harvestAndReport()` revert with `!cooldown`.

Management can convert the donated balance or enable `ignorePending`, but an attacker can repeat the donation. Ignoring pending value also disables protection for legitimate unsettled principal. The Avant integration remains WIP and no deployment was verified, but the same path is present in its source.

### Recommendation

Track only settlement tokens produced by strategy-initiated claims. Increment tracked balances from measured claim output, decrement them during conversion, and exclude unsolicited balances from the report gate. Add regression tests that repeat a donation after management recovery.

## [Medium] Non-atomic settlement and reporting lets early exits shift losses

### Details

Cooldown claims deliver base assets without updating Tokenized Strategy accounting. Those assets immediately increase `availableWithdrawLimit()`, while withdrawals continue using the last reported `totalAssets` and PPS.

If a recovery valued at 100 settles for 80, an early holder can withdraw at the stale valuation before `report()` records the loss. In a two-holder example with 100 tracked assets and 100 shares, redeeming 50 shares pays the first holder 50, leaving only 30 actual assets for the remaining 50 shares. The eventual 20-asset loss is therefore borne entirely by later holders.

Claims are management-only and can be atomically bundled with accounting updates, but the contracts do not enforce that sequence.

### Recommendation

Block exits whenever settlement has changed balances but has not been reported. Clear that state only during an atomic strategy report, and atomically update any parent Vault that carries the strategy at its previous valuation.

## [Medium] Global Lender liquidity can make advertised exits revert after loss

### Details

`availableWithdrawLimit()` includes the Lender’s entire base-asset balance, including liquidity economically belonging to other Lender holders. After an inner-Lender loss but before the outer strategy reports it, the outer strategy can therefore advertise its stale position value as withdrawable.

`_freeFunds()` then converts the requested assets at the current lower inner PPS without capping the resulting shares to the outer strategy’s balance. The inner `redeem()` reverts when those shares exceed what the strategy owns. Consequently, an ordinary exit admitted by `maxWithdraw()` or `maxRedeem()` may be unexecutable.

### Recommendation

Limit advertised Lender liquidity to the minimum of global idle liquidity and the current asset value redeemable by the strategy’s own shares. Cap redemption shares by `LENDER.maxRedeem(address(this))`, and test the composition of multiple Lender holders, an inner loss, and stale outer accounting.

## [Low] Existing idle assets can make maximum deposits revert

### Details

`availableDepositLimit()` returns the Lender’s remaining headroom without considering base assets already idle in the outer strategy. Tokenized Strategy deposits subsequently deploy the strategy’s entire loose balance, not only the new deposit.

With one idle unit and 100 units of Lender headroom, `maxDeposit()` advertises 100, but the transaction attempts to deposit 101 into the Lender and reverts. Funds are not lost, and smaller deposits or management cleanup remain available.

### Recommendation

Cap `_deployFunds()` by the Lender’s current `maxDeposit`, leaving excess assets idle, or subtract existing idle assets when calculating the advertised deposit limit. Test deposits at exactly the reported headroom with a pre-existing idle balance.

## [Low] Exact-asset withdrawals can revert because inner shares are rounded down

### Details

`_freeFunds()` uses `LENDER.convertToShares(amount)`, which rounds down, before redeeming those shares. At a non-integral inner PPS, the redemption can return slightly less than the exact amount requested.

The outer Tokenized Strategy treats that remainder as a loss. Standard `withdraw()` permits zero loss by default and therefore reverts even when the position is healthy and sufficient liquidity was advertised. The discrepancy is normally limited to rounding dust; `redeem()` or a nonzero loss allowance can avoid it.

### Recommendation

Use `previewWithdraw()` to calculate the round-up share amount, capped by the strategy’s `maxRedeem`. Add a test with a non-integral inner PPS, zero outer idle assets, and a standard exact-asset withdrawal.

## [Informational] Unsolicited Lido requests may create an unbounded report denial

### Details

The Lido integration enumerates every withdrawal request returned for the strategy address and loops over the complete list during reporting. It does not track only strategy-originated request IDs or impose a bound.

If Lido permits outsiders to create requests owned by the strategy or transfer withdrawal requests to it, one request above dust could block reports and many requests could make reporting exceed practical gas limits. The prepared evidence did not contain the exact Lido implementation needed to establish those ownership semantics.

### Recommendation

Verify arbitrary-owner creation, NFT transfer, enumeration, pruning, and minimum-request behavior against the exact intended Lido implementation. If reachable, track strategy-created request IDs and process them through a bounded or paginated mechanism.

## [Informational] Settlement liveness has no bounded conservative recovery

### Details

Reports remain blocked while a recorded auction is uncleared or pending cooldown value exceeds dust. The Avant flow additionally depends on an off-chain delegated signer and external order execution for AVETH-to-WETH settlement.

There is no timeout state that conservatively writes down an unavailable claim while preserving later recovery accounting. `ignorePending` restores reports only by omitting the pending value, potentially recognizing a loss. No live auction depth, queue service level, or Avant deployment was available to determine whether prolonged blocking is practically reachable.

### Recommendation

Define bounded recovery procedures for expired auctions, unavailable queues, and signer failure. Add an explicit write-down state that pauses exits, reports the loss consistently, and accounts for any later recovery as such. Validate the maximum blocked duration at intended position sizes.

## [Informational] Post-cutover deployment and external behavior were not verified

### Details

The prepared evidence contained no post-cutover runtime bytecode, constructor arguments, role assignments, limits, concrete parent-Vault configuration, or pinned external-protocol state. Earlier deployment comments predate the mandatory cutover. The Avant deployment script still contains a zero-address Lender placeholder.

Accordingly, the findings above apply to descendant source `cbc52f043818dd6ab360ebe020dae52b7b7098d3`; they do not establish which paths are deployed or the amount of live capital exposed.

### Recommendation

Reproduce runtime bytecode from the exact source and pinned dependencies, compare it with each intended deployment, resolve constructor parameters and roles, and execute the focused tests against a pinned snapshot containing the concrete Vault and external integrations.
