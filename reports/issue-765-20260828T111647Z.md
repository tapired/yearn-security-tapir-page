# Security Review of Yearn Strategy Issue #765

## [Medium] Management can manufacture a loss and capture depositor principal

### Details

At `9702f4c`, `BaseLSTAccumulator.estimatedTotalAssets()` discounts all deployed and pending assets by the mutable `reportBuffer`. Management can set the buffer to 9,999 bps, bypass the health check, report an artificial loss, enable an attacker deposit at the depressed price, restore the buffer, and report the assets again. With 100 WETH backing 100 shares, this permits a 0.01 WETH deposit to mint approximately 100 shares and capture roughly half the restored principal. The attack requires malicious or compromised management, but preventing management from taking principal is an explicit Yearn V3 trust boundary.

### Recommendation

Do not apply a management-controlled buffer to reported asset value. Apply conservatism only to deposit or allocation limits, or make any accounting discount immutable and tightly bounded. Deposits should also remain disabled after unexpected losses until a trusted pre-loss price check is satisfied. Add an end-to-end regression test covering the complete loss, deposit, restoration, and redemption sequence.

## [Medium] Loose tokens can bypass child-vault capacity and block reports

### Details

`Strategy4626._stake()` wraps all loose stETH and deposits all loose wstETH without bounding the amount by the child vault’s current `maxDeposit()`. This occurs even when `_harvestAndReport()` passes zero because the child has no remaining capacity. An unprivileged account can therefore donate one unit of wstETH and make every subsequent report revert while the child is capped, paused, shut down, or no longer accepting the strategy. Curve output above the input amount creates the same mismatch at finite capacity.

### Recommendation

Bound the actual wstETH deposit by `vault.maxDeposit(address(this))`, return without calling the child when capacity is zero, and leave excess tokens loose and accounted for. Test zero capacity, finite capacity, direct token donations, and Curve output above the requested staking amount.

## [Medium] Keeper calls can redeploy emergency liquidity after shutdown

### Details

The framework permits `tend()` and `report()` after shutdown. The target’s `_tend()` and `_harvestAndReport()` can then pass all idle WETH back through `_stake()` without checking shutdown, `stakeAsset`, or `depositLimit`. A keeper can consequently redeploy funds recovered by emergency administration, reducing immediately available withdrawal liquidity and frustrating shutdown recovery.

### Recommendation

Prevent every deployment path from staking when the strategy is shutdown. Route report and tend deployment through one helper that enforces shutdown and capacity policy, while still allowing reports to value existing positions. Test both keeper entry points after emergency withdrawal with `depositLimit = 0` and `stakeAsset = false`.

## [Medium] The factory accepts ERC-4626 children that cannot be exited

### Details

The constructor verifies only that the child’s asset is wstETH, and the factory describes the child as an ERC-4626 vault. Deposits use the standard ERC-4626 API, but every unwind path calls Yearn’s nonstandard four-argument `redeem`. A standard ERC-4626 child can therefore accept all funds and subsequently revert on manual redemption, normal freeing of funds, and emergency withdrawal. The tests create a standard OpenZeppelin mock but replace it with a Yearn strategy before exercising this behavior.

### Recommendation

Either restrict construction to verified Yearn-compatible children and validate the required interface/version, or use the standard three-argument redemption API with local before-and-after balance checks for loss enforcement. Retain the standard ERC-4626 mock in a complete deposit, withdrawal, and emergency-exit test.

## [Low] Curve execution exposes stETH discount value to sandwiching

### Details

The staking path uses a same-transaction Curve quote to choose the route but sets minimum output to only the WETH input. When stETH trades below parity, a searcher can buy first, move the pool toward 1:1, let the strategy execute at the worsened price, and sell afterward. The strategy remains protected from receiving less than nominal principal, but the searcher can capture discount value that otherwise belongs to the strategy. Material profitability depends on pool state and allocation size.

### Recommendation

Enforce a minimum return derived from an independent or previously committed price bound rather than only the manipulable in-transaction quote. Use bounded slippage and protected execution for material allocations, and quantify the threshold with a fixed-state Curve sandwich test.

## [Low] Manual claims can desynchronize pending-withdrawal accounting

### Details

`manualClaimWithdrawals()` accepts an arbitrary subset of request IDs and a Boolean that either clears the entire aggregate pending amount or leaves it unchanged. Clearing after a partial batch omits still-pending requests from estimated assets; claiming everything without clearing leaves a stale nonzero report gate. The function is management-only and the default health check limits immediate exploitation, but operator error or a health-check bypass can realize incorrect accounting.

### Recommendation

Track the nominal amount associated with each request and decrement the aggregate only for requests actually claimed. Remove the whole-aggregate Boolean, account explicitly for any claim shortfall, and test partial batches, repeated claims, and report recovery.

## [Informational] Exact Lido staking-limit and claim behavior remains unverified

### Details

The target checks only `isStakingPaused()` before submitting ETH and records withdrawal requests at their nominal stETH amount. No pinned Lido implementation was provided to establish whether a depleted live staking limit can coexist with an unpaused state, or whether queue claims can return less ETH than recorded. The former could revert deposits and reports; the latter leaves a nonzero residual that blocks reports until management clears it.

### Recommendation

Pin the exact Lido and withdrawal-queue revisions used by the deployment. Test an exhausted live stake limit with staking unpaused and claims returning less than their nominal request, including the intended accounting and report-recovery paths.

## [Informational] The stated combined APR calculation is not established

### Details

The reviewed 4626-branch oracle returns a fixed 4% rather than the stated child-plus-LST, debt-delta-aware APR. A sibling oracle also omits child-vault value. No evidence identifies which oracle, if any, is registered for the claimed strategy, so production reachability and allocator impact cannot be determined.

### Recommendation

Provide the registered oracle address and configuration. If this strategy is allocator-controlled by that oracle, implement and test the weighted child and LST yield calculation across positive and negative debt changes; otherwise explicitly exclude the local oracle from the deployment specification.

## [Informational] Claimed deployments are not reproducibly linked to reviewed source

### Details

The resolved final source is `9702f4c` with Tokenized Strategy `8280628` and periphery `fc1b1d4`, while the initial issue hash predates review fixes. The prepared evidence contains deployment addresses but no creation/runtime bytecode, compiler metadata, constructor values, or matching final broadcast. The exact child implementation, parent Vault V3 revision and queue, roles, hooks, and protocol configuration are also absent. Consequently, the source findings above are not assertions about verified deployed bytecode or external behavior.

### Recommendation

Reproduce both claimed deployments from the pinned commits, Solidity configuration, dependencies, and constructor immutables, then compare creation and runtime bytecode. Preserve the child implementation and compatibility behavior, live roles and deposit controls, parent revision and queue, APR registration, and relevant protocol configuration as review evidence.
